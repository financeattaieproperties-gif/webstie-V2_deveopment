# V2 private website chat migration

Target only `https://website.attaieproperties.com`. Do not copy from, test against, or change V1. This is a manual deployment step, not an automatic installer. No hosted migration has been performed by preparing this source.

1. Confirm the V2 document root and every other public document root in cPanel. Back up existing V2 chat data and private configuration before changing files.
2. Pause website chat writes during the copy. Download the existing V2 `uploads/chat_store/conversations.json` privately. Do not put this download in source control, an upload ZIP, or another document root.
3. Create a directory inside the private V2 configuration area, outside **all** document roots. Permit only the hosting account/PHP process to read and write it. PHP needs `mysqli`, `mbstring`, JSON, cryptographic randomness, file locking, and atomic file rename support. PHP 8.1 or newer is required by the chat service.
4. Copy `conversations.json` into that directory without changing its contents. Verify the copy's byte count and SHA-256 hash against the original. The file must contain a JSON array. Preserve the original backup if validation fails; the new service refuses corrupt data rather than replacing it.
5. Set `WEBSITE_CHAT_STORE_DIR` in the **private V2 website configuration** (or the hosting PHP environment) to that directory's absolute path. This is not a URL. Leave real paths and credentials out of committed templates. A missing, public, inaccessible, or corrupt store returns HTTP 503 and must not be reported as delivered.
6. Upload the newly prepared V2 package when available. Never upload the private directory or configuration. Requests must use the revised customer client and website Admin session/CSRF client together. The packager must explicitly include `chat-service.php`; older packages that block it do not provide this feature.
7. Verify the private store is unreachable over HTTPS, then test two separate browsers: customer sends; website Admin receives; Admin replies; customer receives; refresh preserves the thread; offline messages show pending and recover once. Verify an unrelated customer cannot fetch, send, mark read, or type in another thread. Staff Firebase sessions must not authorize Admin actions. Confirm chat does not create website form inquiries or CRM records.
8. Preserve the old public store backup privately. Remove the former **V2** web-accessible copy only after the copied data and hosted checks are confirmed and rollback is agreed. Do not run a recursive cleanup against a computed hosting path.

Existing ID-only threads remain visible to website Admin after copying. They have no secure ownership proof, so the new public client starts a new secure thread instead of letting anyone claim historical messages by supplying an old ID. Reconnecting an old thread requires a separately verified ownership/recovery process; this release does not invent one. Keep the historical data and explain this to Admin before rollout.

New customer threads use a random 256-bit capability retained on the customer's device. The server stores its hash and requires the capability for reads and mutations. It is never placed in a URL or Admin list response. Client message UUIDs deduplicate retries under the file lock, including an upstream commit followed by a lost response. Clearing browser storage removes that device's ability to reopen its thread.

For rollback, pause writes, preserve the new private store and its hash, restore the reviewed V2 code/configuration backup, and verify the restored behavior on the testing origin. Do not replace newer messages with an older backup without an owner-approved data recovery decision. Hosted upload, private-path protection, permissions, and cross-browser acceptance remain pending until actual server observations are recorded.
